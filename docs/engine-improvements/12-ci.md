# 12 — Continuous integration for the engine (and backend)

**Status:** not started
**Effort:** small (one workflow file; grows with doc 01)
**Elo:** none directly — protects every other change

## Summary

Nothing runs the tests automatically. The only workflow,
`.github/workflows/release.yml`, **builds** the Windows engine when a `v*` tag
is pushed and attaches the `.exe` to a GitHub Release. It doesn't run `ctest`,
doesn't build on Linux (what production runs), and doesn't touch the backend
tests. Breakage is found when someone happens to run tests locally, or in
production.

A test workflow on every push to `dev`/`main` (and on pull requests) catches
it before deploy.

## What exists

| Check | Where | Runs automatically? |
| --- | --- | --- |
| Engine unit tests (6 suites: board/move, eval, search, TT, book, time manager) | `engines/jewkiebot/tests/*.cpp`, `ctest -L tests` | No |
| Engine perf tests | `tests/Performance/*`, `ctest -L performance` | No (and shouldn't — noisy on CI runners) |
| Engine build, Windows | `release.yml` | Only on tag push |
| Engine build, Linux (prod) | `docker/jewkiebot.Dockerfile` in the dss repo | Only at deploy |
| Backend tests (`bun test`, 351 tests, ~100 s locally) | `backend/tests/**` | No |
| Frontend build | `frontend/` | No |

Notes:
- `time_manager_test` takes ~25 s (it sleeps on the wall clock). Fine for CI.
- The full backend suite took ~101 s locally, partly because some integration
  tests spawn processes. Fine for CI.

## Design

A new `.github/workflows/ci.yml`, triggered on `push` to `dev`/`main` and on
`pull_request`. Three independent jobs so failures are easy to read:

```yaml
name: CI

on:
  push:
    branches: [dev, main]
  pull_request:

jobs:
  engine-linux:
    runs-on: ubuntu-latest           # matches prod (Debian, g++)
    defaults:
      run:
        working-directory: engines/jewkiebot
    steps:
      - uses: actions/checkout@v4
      - name: Install toolchain
        run: sudo apt-get update && sudo apt-get install -y cmake ninja-build g++
      - name: Configure
        run: cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
      - name: Build
        run: cmake --build build
      - name: Unit tests
        run: ctest --test-dir build -L tests --output-on-failure
      # Added once doc 01 lands:
      # - name: Perft
      #   run: ctest --test-dir build -R perft --output-on-failure
      # - name: Bench signature
      #   run: ./scripts/check-bench.sh   # compares against "Bench: N" in the commit message

  engine-windows:
    runs-on: windows-latest          # what the release workflow ships
    defaults:
      run:
        working-directory: engines/jewkiebot
    steps:
      - uses: actions/checkout@v4
      - name: Add MinGW to PATH
        shell: pwsh
        run: echo "C:\msys64\mingw64\bin" | Out-File -Append -FilePath $env:GITHUB_PATH -Encoding utf8
      - name: Configure
        shell: pwsh
        run: cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release
      - name: Build
        shell: pwsh
        run: cmake --build build -j4
      - name: Unit tests
        shell: pwsh
        run: ctest --test-dir build -L tests --output-on-failure

  backend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
      - run: bun install --frozen-lockfile
      - run: bun test
```

Details to check when implementing:

- **Linux build warnings.** The engine has only ever been built for release on
  Windows (MinGW) in CI; prod builds on Debian in Docker. A Linux CI job will
  surface any GCC/Linux-only issues early.
- **Static link flags.** The test executables link with
  `-static -static-libgcc -static-libstdc++` (`CMakeLists.txt`). On Ubuntu that
  needs static libstdc++ (installed with g++) and works; if `-static` fails for
  pthread, drop `-static` on Linux.
- **Backend tests that need external things** (engine binaries, network,
  Lichess): check whether any test expects a built engine or network access
  and either build the engine first in the same job or mark those tests to
  skip in CI (`CI=true` env).
- **Caching** (later): `actions/cache` for the CMake build dir and bun's cache
  speeds runs up; not needed at first.

## Bench signature check (after doc 01)

Once `bench` prints a stable `Bench: <nodes>` line (doc 01, layer 2), adopt
the Stockfish convention: every commit that changes search/eval includes
`Bench: <nodes>` in its message. A tiny script compares the built engine's
bench to the most recent `Bench:` line in the commit log and fails the build
on mismatch. This catches "I thought this was a refactor but it changed
behavior" and "the binary doesn't match the source".

## Branch protection (optional)

On GitHub, require the CI checks to pass before merging into `main`. With the
`dev` → `main` flow used so far (`git push origin dev:main`), that means CI
must be green on `dev` first. Keeps prod (which builds from `main`) safe.

## Verification

- Push a branch with the workflow: all three jobs green.
- Push a deliberately broken commit (e.g. flip an assert in a test) on a
  scratch branch: the matching job goes red. Delete the branch.
