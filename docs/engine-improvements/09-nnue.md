# 09 — NNUE: neural-network evaluation

**Status:** not started — long-term project
**Effort:** large (weeks)
**Elo:** roughly +200–400 over a well-tuned hand-written eval
**Depends on:** docs 01 (SPRT), 02, 03, 05 (a sound, reasonably strong search); doc 04 is optional (NNUE replaces the hand-written eval)

## Summary

NNUE ("efficiently updatable neural network") replaces the hand-written
evaluation with a small neural network that's cheap enough to run at every
node. It's how Stockfish and essentially every top engine evaluate today, and
many hobby engines have gained 200+ Elo switching to it. It's the largest
ceiling available — and the largest project.

## How it works

- **Input:** for each perspective (side to move, and the other side), a
  one-hot vector of 768 features: 2 colors × 6 piece types × 64 squares
  ("piece P of color C on square S"). Typically ~30 features are active.
- **Accumulator (first layer):** a 768 → N matrix (N = 128–1024; 256 is a
  good start). The first-layer output for a position is the sum of the
  columns for its active features. **This is the "efficiently updatable"
  part:** a move only changes 2–4 features, so the accumulator is updated by
  adding/subtracting a few columns in `makeMove`/`unmakeMove` instead of
  recomputing.
- **Output:** activation (CReLU or SCReLU) on both perspectives'
  accumulators, concatenated (side to move first), → a single output neuron
  = the evaluation. Larger nets add hidden layers; a single hidden layer
  ("768 → N ×2 → 1") is the standard first net.
- **Quantization:** weights stored as `int16`, so inference is integer SIMD
  math. Net file size for 768→256×2→1 is ~400 KB.

## What it takes

### 1. Data generation (the expensive part)

Train on positions labeled with **search scores** (and game results), produced
by the engine itself:

- Add a `datagen` mode to the engine: play self-play games at a fixed small
  node count (e.g. 5,000 nodes/move) from randomized openings (a few random
  moves, then play), and record `(fen, score, result)` for quiet positions.
- Volume: a first useful net needs on the order of **100M+ positions**; good
  nets use billions. At ~5k nodes/move and ~1M nps per core, one core produces
  very roughly 100–200 positions/second → ~0.5–1 day for 100M on 16 cores.
- Use the *improved* engine (after docs 02–05) for datagen — better search =
  better labels.
- Iterate: train net 1 on data from the hand-written eval, then generate new
  data with net 1, train net 2, and so on. Each generation typically gains.

Requires `go nodes N` to actually work (currently parsed but ignored —
`handle_go` TODO in main.cpp), or a dedicated datagen loop inside the engine
(better: no UCI overhead).

### 2. Training

Use an existing trainer rather than writing one:

- **bullet** (Rust, GPU, by jw1912) — the de-facto standard for hobby engines
  now; supports the simple architectures above and outputs quantized nets.
- Alternatives: the Stockfish `nnue-pytorch` trainer (heavier, built for SF's
  architecture).

Needs a GPU for reasonable training times (a consumer NVIDIA GPU is fine;
CPU training of small nets is possible but slow).

Training objective: a blend of search score (converted to win probability via
a sigmoid, like Texel) and game result, e.g. `0.75·score + 0.25·result`.

### 3. Inference in the engine

- `Accumulator` per ply (stack), updated incrementally in make/unmake
  (or lazily: mark dirty, update on first eval).
- King moves that cross the board's mid-line or that change the "king bucket"
  (if using king-bucketed inputs later) need a full refresh — for the plain
  768-input net, no buckets, every move is incremental.
- SIMD for the update and the output layer (AVX2 via intrinsics, with a scalar
  fallback). Start scalar, correct first; then vectorize.
- Load the net from a file at startup (`EvalFile` UCI option), or embed it in
  the binary with `incbin` so prod always has it.
- Keep the hand-written eval behind an option during the transition, for
  comparison.

### 4. Testing

- Unit test: the incremental accumulator after any make/unmake sequence equals
  a from-scratch refresh (run over perft-style move walks).
- SPRT: net N vs. hand-written eval, then net N+1 vs. net N.
